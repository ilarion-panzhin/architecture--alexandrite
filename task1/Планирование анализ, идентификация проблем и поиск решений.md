
# 1. Потенциальные и существующие проблемные места в архитектуре системы

## Ресурсы и инфраструктура
- Используется только один инстанс на каждый сервис и базу данных — это создаёт **узкие места и single point of failure**.
- Нет автоматического масштабирования сервисов — при росте нагрузки возможны сбои.
- Базы данных не имеют **реплик** и **шардирования** — это снижает отказоустойчивость и масштабируемость.
- Отсутствует **резервное копирование и восстановление** (не указано в описании, нужно уточнение).
- Архитектура не готова к дальнейшему масштабированию бизнеса.

## Наблюдаемость и отладка
- Отсутствует **система логирования**.
- Отсутствует **система мониторинга**.
- Нет **системы трассировки** для отслеживания цепочек вызовов между сервисами.
- Нет информации о **кешировании** в MES, особенно для дашборда заказов — это может быть одной из причин медленной загрузки.

## CI/CD и тестирование
- **Ручной деплой** в release и production окружения.
- Нет **полноценного CI/CD пайплайна** для быстрого релиза, откатов, автоматических проверок.
- **Тестирование ограничено**: используются только юнит-тесты и ручное тестирование QA-инженером.
- Отсутствуют автоматические:
  - **E2E-тесты**
  - **Интеграционные тесты**
  - **API-тесты**
  - **Smoke-тесты**
  - **Регрессионные тесты**

## Команда
- Только один QA-инженер — не справляется с ростом количества функционала.
- Один DevOps-инженер — потенциальное узкое место в обслуживании инфраструктуры.
- Нет отдельного специалиста по автоматизированному тестированию или производительности.

# 2. Инициативы для устранения проблем в системе


## Ресурсы и инфраструктура

- Перевести инфраструктуру на **Kubernetes** с использованием **Helm-чартов**.
- Использовать **managed Kubernetes** (например, в Yandex Cloud) для снижения нагрузки на DevOps.
- Настроить **Horizontal/Vertical Pod Autoscaling (HPA/VPA)** для масштабирования по нагрузке.
- Внедрить **шардирование** и **репликацию** баз данных.
- Ввести **резервное копирование и мониторинг восстановления** данных.
- Разделить окружения dev/release/prod в рамках кластера с изоляцией ресурсов.
- Цель: **обеспечить отказоустойчивость**, **масштабируемость**, **быстрое восстановление** и **удобное управление релизами**.

## Наблюдаемость и отладка

- Внедрить **систему мониторинга**: Prometheus + Grafana.
- Настроить **централизованное логирование**: ELK.
- Добавить **распределённую трассировку**: OpenTelemetry.
- Настроить **систему алертов** (Alertmanager) с уведомлениями в Slack или email.
- Цель: **раннее выявление проблем**, **глубокий анализ производительности** и **отладка межсервисных взаимодействий**.

## CI/CD и тестирование

- Настроить **автоматические CI/CD пайплайны** для всех окружений.
- Внедрить **автоматическое тестирование** на всех этапах пайплайна.
- Добавить недостающие уровни тестирования:
  - Unit-тесты
  - Интеграционные тесты
  - E2E-тесты
  - API-тесты
  - Smoke и нагрузочные тесты
- Использовать **quality gates** (SonarQube) для анализа кода.
- Внедрить **контрактное тестирование API** (Swagger diff).
- Цель: **ускорить релизы**, **повысить надёжность**, **обеспечить регрессионный контроль** и **упростить откаты**.

## Команда

- Нанять:
  - Дополнительного **DevOps-инженера**.
  - **QA-инженера** по автоматизации тестов.
- Ввести **ротацию on-call** для мониторинга инцидентов.
- При необходимости — привлечь **внешнего DevOps-консультанта** на время.

## Архитектурные улучшения

- Добавить **rate-limiting** для публичного API, чтобы защититься от перегрузок.
- Настроить **retry policies и dead-letter очереди** в RabbitMQ.
- Перепроектировать механизм назначения заказов.
- Добавить **кеширование** для медленных запросов, особенно на дашборде MES.
- Цель: **повысить устойчивость**, **снизить задержки** и **улучшить пользовательский опыт**.
